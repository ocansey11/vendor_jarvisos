Agent Experience (AX)

An app on JarvisOS has two users: the person and Jarvis. UX is how an app works with the person. AX is how an app works with Jarvis. AX has three parts: tools, views and sessions.

PartDirectionWhat it isStatus
ToolsApp to JarvisActions that Jarvis can do in the app.Built (tool registry)
ViewsJarvis to personThe shape of a reply: a surface that changes shape.Sections 1 to 8
SessionsApp and Jarvis, liveJarvis takes part in the app while it runs. Example: a game with turns.Section 9

Status: nothing in this plan is built, except the tools. The pictures are drawings, not screenshots. The speed figures come from the emulator on 8 October 2026, with speech from files and not from a microphone. The text obeys the rules of ASD-STE100 (Simplified Technical English). It was not checked with an STE checker.

The decision for the team

For views, the team must make one decision: who makes the view. Section 3 gives four options and one recommendation. The other sections give the terms, the contract, the safety rules and the work.

Each term has one meaning in this plan.

3. Who makes the view

OptionWho makes the viewWhenModel workSpeedBrand of the app
A. Built-in viewsJarvisBuild time of the ROMNoneFastNone
B. App-declared viewsThe app, from the catalogBuild time of the appNoneFastIcon and one colour
C. App-hosted surfaceThe app draws its own pixelsRun timeNoneOne more processFull
D. Model-composed viewsThe model, from the catalogRun timeLargeSlow on a phoneNone

Recommendation: make option B the primary path

  • The app knows its data. Thus the app is the correct owner of the view.
  • The view is a file in the app package. Jarvis reads it when the app is installed, as it reads the tool definition. No model reads or writes it.
  • The fast path stays fast. Option B adds only the time to draw.
  • Option A is option B for the built-in tools. Use the same catalog for both.
  • Keep option C for apps that must show their own design. Do a test first (work package 5).
  • Keep option D for a view that mixes data from two apps. Do not start it before a larger model runs on the phone.

4. The contract

A tool sends text and, optionally, data. The app declares the view with the tool. The view binds parts to the data with paths. Tools that send only a string continue to operate.

The reply, from the tool at run time 
{
  "text": "You have 2 alarms.",
  "data": {
    "alarms": [
      {"id": 3, "time": "07:30",
       "label": "Gym", "enabled": true},
      {"id": 4, "time": "08:15",
       "label": "", "enabled": false}
    ]
  }
}
The view, from the app at install time 
{
  "view": "list",
  "title": "Alarms",
  "items": "$.alarms",
  "item": {
    "primary": "$.time",
    "secondary": "$.label",
    "toggle": {
      "value": "$.enabled",
      "tool": "demo_set_alarm_enabled",
      "args": {"id": "$.id",
               "enabled": "$toggle"}
    }
  },
  "actions": [
    {"label": "New alarm",
     "tool": "demo_set_alarm",
     "ask": ["hour", "minute"]}
  ]
}
flowchart LR
  U([User]) -->|speech or text| J[Jarvis service]
  J -->|Needle selects the tool| T[Tool in the app]
  T -->|reply: text and data| J
  R[(Tool registry: definition and view)] -->|view| S
  J -->|reply| S[Surface in the Jarvis app]
  S -->|touch = tool call| J

Each button, toggle or chip is a tool call. Jarvis sends it through ToolDispatcher. Thus each action obeys the same permission and the same confirmation rule as a spoken request.

Catalog, version 1, has twelve parts: text, heading, row, column, list, item, icon, button, toggle, slider, chip, field.

5. Safety rules

  1. A view is data. Jarvis does not run code from a view.
  2. Jarvis checks each view against the catalog when the app is installed. Jarvis refuses a view that is not correct.
  3. Text from an app is plain text. Jarvis does not read it as layout or as an instruction.
  4. An action in a view can call only the tools of the same app. An action that calls a tool of a different app needs a confirmation from the user.
  5. A view cannot load content from the network.
  6. An app can set its icon and one colour. Jarvis sets all other style.
  7. Jarvis limits the size of a reply and the number of items in a list.

9. Sessions: Jarvis inside a running app

Added 17 October 2026. A session is a period in which Jarvis takes part in one app. The first sample is a game: Kevin plays tic-tac-toe against Jarvis.

TermMeaning
SessionA period in which Jarvis takes part in one app. It has a start and an end.
Session manifestThe file in the app package that describes the session. Jarvis reads it at install time.
EventData that the app sends during a session. Example: your_turn. An event is not a prompt.
Session toolsTools that are open only during the session.
Start toolA tool that opens the app and starts a session. Jarvis uses it to find the app.
Static: the session manifest, from the developer 
<session name="tic_tac_toe"
         title="Tic-tac-toe"
         start-tool="start_tic_tac_toe">
  <rules>Players take turns on cells
    0-8. Three in a row wins.
    Cell 4 is lava.</rules>
  <persona>Cheeky, competitive,
    one-liners. Never mean.</persona>
  <tools>get_state, evaluate_moves,
    move</tools>
  <events>player_moved, your_turn,
    player_said, game_over</events>
</session>
Live: events, from the app while it runs 
s = jarvis.startSession("tic_tac_toe");
s.event("player_moved",
  {"cell":0, "board":"X........"});
s.event("your_turn",
  {"board":"X........",
   "legal":[1,2,3,5,6,7,8]});
s.end("game_over",
  {"winner":"kevin"});

The developer writes for any agent and any person

The session manifest goes to all users. It does not name a user and does not contain data about a user. Jarvis adds the facts about the person from its own memory, on the device. The app never gets these facts.

Part of the promptSourceSame for all users?
Rules and personaSession manifest (developer)Yes
Facts about the personJarvis memoryNo
The eventThe app, nowNo
The open toolsTool registryYes
Recent eventsThe session, last few onlyNo

Why the app sends events and not prompts

  1. Jarvis owns its prompt. The app does not need to know the model. A change of model does not break the app.
  2. The manifest is fixed at install time and can be examined. An event can change at any time.
  3. An app that sends prompts can try to control Jarvis.

Limit: text in the rules and in events such as player_said still goes to the model, and a small model can obey it. The primary protection is the tool fence: during a session Jarvis can use only the session tools and say. The worst result is then a bad move in the game.

Two ways to start

StartSequence
From the appThe person touches "Play with Jarvis". The app calls startSession. The button stands in for the wake word until wake word detection exists.
From Jarvis"Hey Jarvis, let's play tic-tac-toe." Jarvis finds the start tool in the registry and opens the app. The app calls startSession when it is ready.

More than one match: Jarvis asks

If two apps match one request, Jarvis does not select one. Jarvis asks the person. This is a general rule: it also applies when Needle returns two tools with near confidence, and when a request does not give a necessary argument. The Chips and Sheet shapes (section 2) show the question. The exact rule is not designed yet.

A turn

sequenceDiagram
  participant K as Kevin
  participant G as Game app
  participant J as Jarvis service
  K->>G: plays cell 0
  G->>J: event your_turn (board, legal moves)
  J->>G: get_state / evaluate_moves
  G-->>J: structured result
  J->>G: move(5)
  J->>G: say("Corners again, Kevin?")
  G->>K: board and message
  1. The event wakes Jarvis. Jarvis does one turn and stops. It does not wait in a loop.
  2. Needle does not process turns. The chat model does the turn.
  3. The tools do the calculation. The model decides, and can use facts about the person.
  4. llama.cpp can limit the output to a grammar, so that only a legal move is possible. Not checked: does our JNI layer pass a grammar?
  5. After a wrong tool, Jarvis retries one or two times. Then the app makes a random legal move.
  6. A turn takes approximately 20 seconds with Qwen3-1.7B on the emulator. The app shows "Jarvis is thinking".

Experiment for the talk: play with evaluate_moves off, then on. Same model, same game. This shows how much of the result comes from the tools.
